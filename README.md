# MiniAgent

A minimal agent built with Node.js, TypeScript 7, and the [AI SDK](https://ai-sdk.dev) —
using plain SDK primitives (`streamText` / `generateText` + tools + a step loop)
rather than the SDK's own `ToolLoopAgent` abstraction.

## Requirements

- [Node.js](https://nodejs.org) >= 20
- [pnpm](https://pnpm.io) (`corepack enable` or `npm i -g pnpm`)

## Setup

```sh
pnpm install
```

Then set your credentials. `App.run()` reads `config.json` from the data
directory (`$HOME/.config/miniagent/config.json` in a release build,
`.miniagent/config.json` in the checkout) and always merges `.env` from the
current directory into the environment (see [src/app/app.ts](src/app/app.ts)); variables
already set in the environment win, and a missing file is not an error.

```jsonc
// <dataDirectory>/config.json — every field is optional
{
  "provider": "openai",
  "model": "gpt-6-astra",
  "providers": {
    "openai": { "apiKey": "sk-..." },
    "ollama": { "baseURL": "http://localhost:11434/v1" },
  },
}
```

```sh
# equivalent environment fallbacks
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-6-astra
# optional, session id; when unset, the Context generates one
MINIAGENT_SESSION=default
# optional, overrides the context window read from the model catalog
MINIAGENT_CONTEXT_WINDOW=128000
# optional, tees diagnostics to a file as well as stdout
MINIAGENT_LOG_FILE=.miniagent/miniagent.log
# optional, quietest log level emitted (debug, info, warn, error)
MINIAGENT_LOG_LEVEL=info
```

Without `MINIAGENT_LOG_FILE` (or `--log-file`), diagnostics tee to the
console and `<dataDirectory>/log/latest.log`, renamed to the local finish
time (`2026-10-12_14-30-00-042.log`) when the run ends. With a log file,
diagnostics tee to the console and that file instead. A run that logs
nothing still keeps its (empty) timestamped file.

For a fresh session the config file wins over the environment: provider =
`config.provider` else `openai`; model = `config.model` else `OPENAI_MODEL` else
`gpt-6-astra`; API key = `config.providers[provider].apiKey`, else the
provider's env var (`OPENAI_API_KEY`) resolved inside the AI SDK. A stored
session keeps the provider and model it was created with, whatever the config
file now says.

## Usage

```sh
pnpm dev                                  # or: pnpm start
```

The command line is defined in [src/cli.ts](src/cli.ts) with
[commander](https://github.com/tj/commander.js). It parses the options and boots
the app with the resulting prompt:

```sh
miniagent [options] [prompt]

Options:
  -v, --version       output the version number
  --log-file <path>   tee diagnostics to a file as well as stdout
  --log-level <level> quietest log level to emit (debug, info, warn, error)
  -h, --help          display help for command
```

`-v` / `--version` prints the build version and exits without loading any
configuration:

```sh
pnpm start -- --version
```

`App.run()` only loads the configuration and builds the agent: it merges `.env`,
reads `config.json`, restores the session's `Context` (which keeps its stored
provider and model), resolves its context window from the
[models.dev](https://models.dev) catalog, and constructs the `Agent` through the
provider registry. The resolved values are then exposed for whatever drives the
conversation:

```ts
const app = new App()
const code = await app.run()

app.sessionId // MINIAGENT_SESSION, or the id generated by the Context
app.context?.id // same id the session's Context was loaded or created with
app.providerId // provider id the session runs on
app.modelId // model id the session runs on
app.context // the session's Context, window resolved
app.agent // the built Agent (or the injected one), bound to app.context
app.agentFor(context) // builds an Agent for any session on its own model
app.agents // per-session agent registry; plugins drive agents directly
app.dataDirectory // .miniagent, or $HOME/.config/miniagent in a release build
app.version // version stamped into this build
```

Providers live in [src/models/providers.ts](src/models/providers.ts): the `Providers` class
holds the AI SDK registry and a table of provider id and create function.
`openai`, `anthropic`, and `google` are built in; `deepseek` registers through
the DeepSeek plugin ([src/plugins/builtin/deepseek.ts](src/plugins/builtin/deepseek.ts)) via
`onProvidersCreating`, and the config file applies through
`providers.loadConfig(settings)`, initialising the provider under the same id
with its settings. Any other id becomes an OpenAI-compatible provider built
from its settings. Adding another built-in is one create function in the
constructor. `providers.add(id, create, { models })` also records model ids,
so a custom provider the models.dev catalog does not list still offers its
models in `/model` completion and in `/models`.

It prints the context-window diagnostics as it resolves them (tagged with
`module: 'app'` in the log line), and
returns exit code `1` when the provider is unknown or its settings are
rejected. The
model cache, the config file, and any persisted sessions live in
`app.dataDirectory`: `.miniagent` in a development build,
`$HOME/.config/miniagent` in a release build. Talking to the user (REPL,
web server, ...) is a layer on top of `app.agent`, not part of `App`.

### Development vs release builds

TypeScript has no build-time `define`, so the release sign is passed as an
environment variable to a small generator that writes it into a source file
before `tsc` runs:

```sh
MINIAGENT_RELEASE=1 pnpm build   # release build
pnpm build                       # development build
```

`scripts/build-info.mjs` writes `src/build-info.ts` (gitignored) holding
`RELEASE` and the `VERSION` from `package.json`; `src/app/paths.ts` imports them and
picks the data directory from `RELEASE`. `build`, `dev`, `typecheck`, and `test`
all run the generator first, and `postinstall` covers a fresh clone.

## The Agent class

`src/agent/agent.ts` exports a small `Agent` class that wraps the AI SDK Core tool loop:

```ts
import { openai } from '@ai-sdk/openai'
import { Agent } from './agent.js'

const agent = new Agent({
  model: openai('gpt-6-astra'), // any AI SDK LanguageModel
  system: 'You are a helpful assistant.',
  tools: { read: readTool }, // any AI SDK ToolSet
  context, // optional member conversation (see below)
  maxSteps: 8, // tool-loop step limit
})

// Submit prompts; each is added to the member context as a user message:
for await (const event of agent.stream('What is 6 * 7?')) {
  if (event.type === 'text-delta') process.stdout.write(event.text)
  if (event.type === 'tool-result') console.log(event.output)
}

// Non-streaming: full result incl. steps, tool calls, usage, responseMessages
const result = await agent.run('What is 6 * 7?')
```

`stream()` event types:

| Event             | Emitted when                                   |
| ----------------- | ---------------------------------------------- |
| `start`           | the run starts                                 |
| `step-start`      | a step (model call) begins                     |
| `text-delta`      | a chunk of answer text arrives                 |
| `reasoning-delta` | a chunk of model reasoning arrives             |
| `tool-call`       | the model requests a tool call                 |
| `tool-result`     | a tool finished and returned its output        |
| `step-finish`     | a step finished (with finish reason and usage) |
| `finish`          | the whole run finished (with total usage)      |
| `error`           | something failed; the run stays alive          |

`run()` returns `text`, `finishReason`, `usage`, `steps`, `toolCalls`,
`toolResults`, and `responseMessages` (append the latter to your message
history to continue a conversation across runs).

Every call takes a prompt string plus an optional `AbortSignal`. Inputs
queue behind the running one and execute in order; `submit()` enqueues
without waiting and returns `{ id, done }`, while `subscribe()` taps the
single output stream of run-tagged events. Without a `context` member
each run is ephemeral. One agent drives one conversation: build one per
session (`App.agentFor`) instead of sharing.

### Context (conversation history)

`src/session/context.ts` exports a `Context` class that stores the conversation
history. Hand it to the `Agent` as its `context` member, then submit
prompts: the current history is sent to the model and the messages generated
during the run — including tool calls and tool results — are appended back into
the context afterwards.

```ts
import { Context } from './context.js'

const context = new Context()
const agent = new Agent({ model, context })

for await (const event of agent.stream('What is 6 * 7?')) {
  if (event.type === 'text-delta') process.stdout.write(event.text)
}

// context.messages: user, assistant (tool call), tool result, assistant (answer)

// next turn sees the full history:
for await (const event of agent.stream('and in hex?')) {
  /* ... */
}
```

The `Context` API: `add(message)`, `addUser(text)`, `addAssistant(text)`,
`append(messages)`, `clear()`, `clone()`, plus `messages` (defensive snapshot)
and `messageCount`. Failed runs do not corrupt the history — nothing is
appended when the run errors.

### Persistence

A `Context` can be bound to a `ContextStore` and an id. The agent then
appends each finished run to the stored history, and `Context.load()`
restores it:

```ts
import { Context } from './context.js'
import { FileContextStore } from './store.js'

const store = new FileContextStore('.miniagent/contexts')

// empty if nothing stored for this id yet
const context = await Context.load(store, 'user-123')

// or let the context generate its own id
const fresh = new Context([], { store })
console.log(fresh.id) // generated UUID

const agent = new Agent({ model, context })
for await (const event of agent.stream('What is 6 * 7?')) {
  /* ... */
}
// → appended to .miniagent/contexts/user-123.json

// later, in another process:
const resumed = await Context.load(store, 'user-123')
console.log(resumed.messageCount) // history is back
```

- `FileContextStore` keeps one JSON Lines file per context id: a header
  (`type: "session"`, `version`, `id`, `createdAt`), then one line per
  finished turn holding the messages it added, the usage it reported, and the
  provider and model it ran on. Each run appends; nothing is rewritten, so a
  crash loses at most the turn in flight.
- The header carries the format version (`SESSION_LOG_VERSION`, currently
  `1`). A file from a newer version is refused instead of rewritten. Files in
  the older single-object format — a bare message array or one snapshot
  object — still load, and the next append migrates them to the log.
- `save()` appends the messages added since the last save. `save({ compact:
true })` rewrites the whole history as one `snapshot` record instead;
  `SessionManager.close()` does that when a session ends, so its log stays
  small. A rewrite also happens by itself after `clear()` or `truncate()`,
  because the log then holds messages the context no longer has.
- Compaction writes are atomic (temp file + rename). An append is a single
  `appendFile`; its one failure mode is a torn last line, which `load()`
  ignores and the next append drops before writing.
- A history file that exists but cannot be read is quarantined aside
  (`<id>.json.corrupt-<timestamp>`) instead of loading as empty, and the
  session starts fresh with a warning. Missing files still mean empty.
- `Context.load()` prefers the stored provider and model; it only falls back to
  the passed options for a fresh or legacy file. That is how a restored session
  keeps working after the config file changes.
- Auto-save is on by default when a store is bound; disable it per context
  with `new Context([], { store, id, autoSave: false })` and call
  `await context.save()` yourself.
- `save()` throws if the context is not bound to a store; `delete(id)` removes
  a stored history. Omit `id` and the context generates one.
- Any backend works — implement the `ContextStore` interface
  (`load` / `save` / `append` / `delete`) for a database, Redis, object
  storage, ...

### Token counting

Token counts come from the provider — there is no local tokenizer. After every
run the agent records the total usage the model reported for the whole run
(all steps), and the context reports it:

```ts
const context = new Context([], { contextWindow: 128_000 })

context.tokenCount // input + output tokens of the last response
context.usage // { inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens }
context.remainingTokens // contextWindow - tokenCount
```

Things worth knowing:

- `tokenCount` is `0` until the first response has been recorded.
- It counts what was sent, so a message you just added is not part of the
  number until the next run.
- `inputTokens` already includes tokens served from the provider's prompt
  cache, so `cacheReadTokens` / `cacheWriteTokens` are reported alongside it
  and not added to `tokenCount` again.
- Providers that do not report usage leave the count at `0`.
- The AI SDK does not ship model context-window sizes. `resolveContextWindow()`
  reads them from the [models.dev](https://models.dev) catalog
  ([src/models/catalog.ts](src/models/catalog.ts)), caches them in
  `<dataDirectory>/models.json` for an hour, and honours
  `MINIAGENT_CONTEXT_WINDOW` as an override. The function is optional and never
  throws; without a window, `remainingTokens` stays `undefined` and the context
  still works.

```ts
import { resolveContextWindow } from './models/context-window.js'

const context = new Context([], { modelId: 'gpt-6-astra' })
await resolveContextWindow(context) // fills in context.contextWindow
```

The count is stored together with the history, so a restored session knows its
size before the next run.

### Tools

Tools live in the basic-tools plugin (`src/plugins/builtin/basic-tools/`) and are
plain AI SDK `tool()` definitions with zod `inputSchema`s. The plugin's
`index.ts` registers them:

- `read` — read a text file, optionally a line slice (offset/limit)
- `write` — create or overwrite a text file, creating parent directories
- `edit` — replace exact text (must occur once, unless `replaceAll`)
- `shell` — run a shell command, returning output and exit code

Relative paths (including a relative shell `workdir`) resolve against the
session's project directory, not the process working directory.

Add a tool by creating a `tool({ description, inputSchema, execute })` and
adding it to the agent's `tools` object. Tool errors (thrown in `execute`)
are surfaced to the model as `tool-error` parts so it can react to them.

### Plugins

Plugins extend the agent without changing the core: tools, providers,
system prompt parts, and a post-build `run` step where a frontend (TUI,
WebUI) drives the agent. Every method is optional — implement only what the
plugin needs.

```jsonc
// <dataDirectory>/config.json
{
  "plugins": ["./plugins/my-tools.js", "miniagent-plugin-foo"],
  "tools": { "read": { "enabled": false } },
  "pluginConfig": { "my-tools": { "verbose": true } },
}
```

A specifier can be a project directory or file path (`./plugins/my-tools.js`,
`./plugins/my-plugin`, or an absolute path), a local package path
(`file:../shared/my-plugin`), or an npm package name (`miniagent-plugin-foo`).
Relative paths resolve against the data directory first, then `process.cwd()`.
A directory resolves through its `package.json` entry (`exports`, then `main`),
else `index.mjs` / `index.js`. Each target must ask back with a `Plugin`
instance: the module's `default` export, `plugin` named export, or the module
itself. A class export is instantiated; a factory function is called. The
instance must have a `name` and at least one method. A class-based plugin looks
the same:

```ts
export default class MyPlugin implements Plugin {
  name = 'my-tools'
  setup(host: PluginHost) {
    host.tools.greet = greetTool
  }
}
```

```ts
import type { Plugin } from 'miniagent'

export default {
  name: 'my-tools',
  onProvidersCreating(providers, config) {
    providers.add('mine', (options) => myProvider(options))
  },
  setup(host, config) {
    host.tools.greet = greetTool
    host.systemPromptParts.push('Be brief.')
  },
  async run(host, config) {
    // runs after the agent is built, concurrently with other plugins'
    // `run` methods. A frontend drives the agent here:
    // for await (const event of host.agent.stream(host.prompt ?? '')) { ... }
  },
} satisfies Plugin
```

Boot order: `onProvidersCreating` runs before the config file's provider
settings apply, so plugin providers still receive their `providers.<id>`
settings. `setup` mutates the live `tools`, `providers`, and
`systemPromptParts`. After the agent is built, every plugin's `run` starts
concurrently; all share one agent and context, so drivers must coordinate
turns between themselves. No plugin implements `run` means headless: `run()`
returns `0` as before.
`tools.<name>.enabled: false` removes a tool after the
merge. A plugin that fails to load or throws fails fast: the app prints the
plugin name plus reason and exits `1`.

## Architecture

Layers, inside out:

- Core: `agent/` (tool loop), `session/` (history + store + sessions),
  `models/` (providers + catalog + context window), `commands/` (slash
  commands), `logging/`. Core never imports from `app` or `plugins` —
  enforced by ESLint zone rules in `eslint.config.js`.
- Plugins: `plugins/` holds the plugin contract (`types.ts`), the loader
  and manager, plus built-ins under `plugins/builtin/` (tools, providers,
  TUI). Plugins see core and plugin types only, never `app`.
- `app/` composes everything: config, sessions, providers, plugins, agents.

Where to add things:

| Add ...         | Touch ...                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------- |
| a tool          | `src/plugins/builtin/basic-tools/tools.ts`, or ship a plugin                                  |
| a provider      | `providers.add(id, create)` in `src/models/providers.ts`, or a plugin's `onProvidersCreating` |
| a command       | register in `App` (`src/app/app.ts`); logic lives in `src/commands/`                          |
| a plugin        | implement `Plugin` (`src/plugins/types.ts`), list it in `config.json` `plugins`               |
| a model default | `src/defaults.ts`                                                                             |

## TypeScript 7 (native compiler)

This project uses the native TypeScript 7 compiler for `tsc` (build/typecheck).
Because TS 7 does not yet expose a programmatic API (planned for 7.1), tools that
need the old compiler API — notably typescript-eslint — still rely on TypeScript 6.
This is handled with npm aliases, per the
[official recommendation](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6.0):

| devDependency        | Aliased to                    | Purpose                                    |
| -------------------- | ----------------------------- | ------------------------------------------ |
| `@typescript/native` | `npm:typescript@^7`           | Native TS 7; provides the `tsc` binary     |
| `typescript`         | `npm:@typescript/typescript6` | TS 6 API for typescript-eslint; `tsc6` bin |

Notes:

- `tsc` runs TypeScript 7 (the ~10x faster native port).
- `tsc6` is available if a tool ever needs the TS 6 CLI directly.
- Once typescript-eslint supports the TS 7.1+ API, you can drop the `typescript`
  alias and use `typescript@^7` as a regular dependency.
